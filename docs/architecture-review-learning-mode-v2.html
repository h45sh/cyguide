Deepening Candidates (Next Iteration)

1. Deepen FlagEditor into a Reusable Command Preview Adapter

High Leverage locality
cyguide/ui/screens/learning.py (FlagEditor lines 50-125) · cyguide/engine/learning.py (RecipeBinding) · cyguide/ui/widgets/flags.py (new)

Motivation

FlagEditor currently lives inside cyguide/ui/screens/learning.py. In lines 101-110, it duplicates macro substitutions ({url}, {target}, {domain}, {port}, and wordlist substitution). When macro logic changes, both the widget and RecipeBinding must be modified. Furthermore, other screens cannot reuse this editor.

Proposed Interface

class CommandPreviewEditor(Widget):
    """Deep UI adapter delegating command construction to RecipeBinding."""

    def __init__(self, tool_name: str, manifest: Optional[Manifest] = None):
        super().__init__()
        self.tool_name = tool_name
        self.manifest = manifest

    def set_target(self, target: str) -> None: ...
    def set_flags(self, flags_list: Sequence[str]) -> None: ...
    def get_invocation(self) -> ResolvedInvocation:
        """Returns fully resolved, validated invocation via RecipeBinding."""
        return RecipeBinding.resolve(
            manifest=self.manifest,
            target=self.target_input.value,
            flags_used=self.flags_input.value,
        )

Depth & Leverage

Depth: Hides live debounced preview formatting, macro substitution, sudo validation, and wordlist resolution behind two simple methods (set_flags and get_invocation).
Leverage: The entire macro replacement logic lives in one place (RecipeBinding), eliminating UI string parsing entirely.

Migration Path

  1. Extract FlagEditor into cyguide/ui/widgets/flags.py as CommandPreviewEditor.
  2. Replace internal string substitution in update_preview() with a call to RecipeBinding.resolve().
  3. Update LearningModeScreen to import the deepened widget.

2. Encapsulate Imperative Card DOM into a RecipeDeck Deep Widget

Clean Interface depth
cyguide/ui/screens/learning.py (select_tool lines 489-563) · cyguide/ui/widgets/recipe_deck.py (new)

Motivation

Inside LearningModeScreen.update_tool_context(), over 80 lines of code imperatively mount labels, badges, headers, action buttons, and recipe cards into recipes_scroll. This clutters the screen with DOM construction and tightens coupling to CSS class hierarchies.

Proposed Interface

class RecipeDeck(VerticalScroll):
    """Deep widget presenting structured workflow recipes and tool reference cards."""

    class RecipeSelected(events.Message):
        """Emitted when user selects a recipe to load or run."""
        def __init__(self, recipe_idx: int, auto_run: bool = False): ...

    class AskAIRequested(events.Message):
        """Emitted when user clicks [✦ ASK AI] on a recipe card."""
        def __init__(self, recipe_idx: int): ...

    async def load_tool_context(self, context: ToolLearningContext) -> None:
        """Single declarative entrypoint rebuilding reference badge and recipe cards."""
        ...
    def set_active_recipe(self, recipe_idx: Optional[int], is_running: bool = False) -> None:
        """Updates card button states (RUN -> STOP) without clearing the DOM."""
        ...

Depth & Leverage

Depth: Hides 80+ lines of nested widget instantiation, CSS styling classes, empty state handling, and button state transitions behind load_tool_context().
Locality: Isolates recipe presentation completely from the screen coordinator.

Migration Path

  1. Create RecipeDeck in cyguide/ui/widgets/recipe_deck.py.
  2. Replace lines 489-563 in learning.py with await self.recipe_deck.load_tool_context(context).
  3. Handle RecipeDeck.RecipeSelected in the screen message handler.

3. Unify Execution Lifecycles Behind an Agnostic InvestigationSession Seam

Architectural Seam seam
cyguide/app.py · cyguide/engine/learning.py · cyguide/engine/power_facade.py · cyguide/engine/session.py (new)

Motivation

Currently, CyGuideApp maintains two separate execution paths: self.power_facade (for Power Mode) and self.learning_session (for Learning Mode). Both sessions talk to GraphStore, ToolRegistry, and ExecutionSession, yet they maintain disjoint state handling for database resets, explainer reloads, and workspace updates.

Proposed Interface

class InvestigationSession(Protocol):
    """Agnostic seam governing both Learning and Power investigation modes."""

    session_id: UUID
    workspace_id: Optional[UUID]

    async def execute_action(self, action: ActionRequest, on_chunk: Callable[[str], Any]) -> UUID: ...
    async def stop_execution(self, job_id: Optional[UUID] = None) -> bool: ...
    async def extract_findings(self) -> Tuple[str, str]: ...
    def reload_subsystems(self, explainer: Optional[ExplanationTutor] = None, store: Optional[GraphStore] = None) -> None: ...

Depth & Leverage

Depth: Eliminates duplicate wiring logic in CyGuideApp.init_engine(), reload_explainer(), and on_database_changed().
Seam: Guarantees that future modes (e.g., automated red-team simulations) plug into the same execution and reporting seam without modifying top-level application orchestration.

Migration Path

  1. Define InvestigationSession protocol in cyguide/engine/session.py.
  2. Make LearningSession and PowerWorkspaceFacade conform to InvestigationSession.
  3. Simplify CyGuideApp to hold active session references uniformly.

4. Stream Event Decoupling for AI Tutor Queries (TutorQueryStream)

Locality interface
cyguide/ui/screens/learning.py (query_ai_tutor lines 836-926) · cyguide/engine/learning.py

Motivation

Currently, LearningModeScreen.query_ai_tutor() spans 90 lines. It manually manages a local interval timer (time.time() - last_chat_update > 0.04), buffer accumulation, fallback greeting text, and error notifications. This mixes stream rate-limiting and domain fallbacks directly with Textual widget manipulation.

Proposed Interface

class TutorQueryChunk(NamedTuple):
    text: str
    is_complete: bool
    is_error: bool = False

class LearningSession:
    async def stream_tutor_response(
        self, question: str, fps: float = 25.0
    ) -> AsyncIterator[TutorQueryChunk]:
        """Deep method: handles rate-limiting, error fallbacks, and yields display-ready chunks."""
        ...

Depth & Leverage

Depth: Absorbs stream pacing, fallback formatting, cancellation safety, and error encapsulation away from the UI screen.
Locality: The screen becomes a 10-line consumer that merely receives text chunks and posts them to the markdown renderer.

Migration Path

  1. Add stream_tutor_response() to LearningSession.
  2. Refactor LearningModeScreen.query_ai_tutor() into a concise consumer loop.
  3. Add unit tests in tests/unit/test_learning_session.py verifying rate limiting and fallback text.
